## [102.0.0] — 2026-10-26

Выпуск «Рабочая платформа»: клиент v101 + ЖИВОЙ бэкенд FastAPI, подтверждённые
совместными испытаниями. Артефакт: `ais_providets_v102.html` (единый HTML).
Сборка: `python3 src11/patch_v102.py` (детерминированная, из `ais_providets_v101.html`).

### Исправлено
- **Д-10 (критический, серверный режим):** обёртка `doLogin` вызывала
  `prepareServerLoginAttempt()`, который очищал `#srvPass` ДО чтения пароля функцией
  `srvTryLogin` — серверный вход через UI (JWT + MFA/TOTP) был невозможен
  («Укажите пароль…»). Дефект присутствовал с Этапа 9 (v100), не обнаруживался
  jsdom-тестами; выявлен браузерными E2E на живом бэкенде. Исправление: снимок пароля
  передаётся аргументом `srvTryLogin(presetPassword)` (вызов без аргумента совместим).
- **Бэкенд `POST /api/v1/ai/run`:** возвращает СОХРАНЁННЫЕ рекомендации с `rid`
  (ранее — сырые результаты расчёта без `rid`); форма ответа совпадает с
  `GET /api/v1/ai/recommendations` — контракт клиентского моста Этапа 9.

### Добавлено
- **Живой протокол интеграции** `src10/live_protocol.py` — **17/17 PASS** против
  реального API: IAM (пароль → mfa_required → TOTP из СУБД → JWT L7), bootstrap из СУБД
  (100 организаций, 12 проектов, 15 модулей, 29 интеграций), цепочка ИВП-1→ИВП-2
  (assign → conclude → `passport.verified` → стимул MOD-STIM), поток статусов MOD-DOC,
  MOD-AI (run → accept → повтор 409), graceful degradation (off → 503), WORM-аудит
  (хеш-цепочка sha256 сверяется), отзыв токена (logout → 401). Протоколы — в
  `src10/protocols/` (статус: EXECUTED_LOCAL_SANDBOX_NOT_INDEPENDENT_ACCEPTANCE).
- **E2E-стенд `srv`** (Playwright): 10 сценариев «клиент против живого FastAPI» —
  серверный вход через UI с MFA-диалогом, доставка событий шины опросом, KPI-пересчёт,
  AI-цикл с принятием рекомендации, EXPERT-цепочка + WORM-запись, негативы
  (неверный пароль/MFA — fail closed, демо не открывается), деградация полного стека,
  отзыв токена, серверный RBAC (L0 → 403).
- **Фактический OpenAPI** (64 пути) экспортирован из живого приложения:
  `backend/openapi_providets.json` / `.yaml` — артефакт ART-02 манифеста релиза.
- **Smoke-проверка SRV-LOGIN-01** — постоянный контроль дефекта Д-10.

### Изменено
- Версия v102.0.0 во всех отчётах/экспортах/UI — автоматически из `APP_VERSION`
  (результат работы 0.1/P3.1: ручных замен версии не потребовалось).
- «Что нового» в справочном центре обновлено до v102.0.0.

### Совместимость
- Демо-режим, киоск, вариант Б — без изменений (регрессия: 87 jsdom + 63×2 E2E).
- Снимки данных v100/v101 восстанавливаются в v102 (schemaVersion=1).

## [100.0.0] — 2026-10-18

### Изменено
- Этап 9 — объединение двух веток разработки и устранение критического дефекта: (1) к закалённой клиентской ветке (v13–v82, работы P0.1–P0.59: XSS/URL-валидация, лимиты ответов API, эпохи сессии, атомарный bootstrap, снимки данных с CRC32 и самодиагностикой, Air-Gap-политика, SBOM-реестр, контрольные ворота выпуска) подключён серверный мост Этапа 8 — MOD-KPI (регламентный пересчёт из СУБД, телеметрия KPI-2/4/5/8, kpi.threshold_breached → авто-санкция MOD-STIM по Прил. 1.6), MOD-EXPERT (детерминированное назначение экспертов, заключения с серверной цепочкой ИВП-1→ИВП-2: арбитраж → паспорт верифицирован → стимул → цифровой двойник, SLA ≤ 8 ч), MOD-DOC (неизменяемый поток Проект → На подписании → Подписан (ЭЦП) → Утверждён, серверная карточка и аудит), MOD-AI (детерминированная модель v4.0-srv: tech-gap к порогу суверенитета 75 %, риск срыва контрольных точек, 6 правил рекомендаций, публикация при confidence ≥ 0.7), MOD-STIM (каталог мер, автоприменение по событиям шины); мост активен только в серверном режиме, демо-режим не изменён, все запросы проходят через закалённый srvApi (валидация адреса, лимит размера ответа, эпоха сессии, таймаут 30 с); (2) исправлен критический дефект страницы «О системе»: malformed-структура массива истории версий приводила к тому, что comma-оператор отбрасывал всё содержимое страницы до истории, а записи v49–v82 не отображались — история реконструирована единым массивом с сортировкой от новых к старым; (2b) исправлены пять дефектов встроенной самодиагностики закалённой ветки: очистка диагностического текста не срабатывала для JSON-ключей в кавычках (api_key, session_id — секрет попадал в отчёты); регекс негативного теста самоссылки организации не совпадал с фактическим сообщением валидатора; проверка сводного P0-пакета вызывала асинхронный сборщик синхронно (выделен синхронный buildP0EvidenceBundleCore); цифровой двойник для негативных тестов снимков отсутствовал до первого открытия MOD-PASS/MOD-PROF — добавлена стартовая сборка двойника E03 (организации, не затрагиваемой негативными тестами); негативные тесты ID организаций не учитывали двойники — копия снимка в тесте теперь исключает двойник переименованной организации (изоляция проверяемого валидатора); (3) унифицированы версионные метаданные (экран входа, примечание прототипа, «О системе», футер, тур оператора, план Фаз 0–6, SBOM, диагностические отчёты и имена JSON-экспортов _v100) — устранён разнобой v82/74/49/37/12; (4) проверки: бэкенд — 80 серверных тестов (pytest, Этапы 1–8), клиент — встроенные smoke-тесты 20 + объединённый набор DOM-тестов Этапа 9, live-сценарий 12 проверок (uvicorn + HTTP-цепочки Этапа 8)
