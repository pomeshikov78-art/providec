# Этап 11 — выпуск v102.0.0 «Рабочая платформа»

**Содержание выпуска:** исправление критического дефекта Д-10 (серверный вход через UI)
+ доказательный комплект «платформа действительно работает»: живой протокол интеграции
(17/17), E2E-стенд `srv` (10 сценариев клиент против живого FastAPI), фактический
OpenAPI (64 пути) вместо черновика.

## Дефект Д-10 (критический, серверный режим)

Обёртка `doLogin` (мост Этапа 9) вызывала `prepareServerLoginAttempt()`, который через
`clearAuthSensitiveFields()` **очищал поле `#srvPass` до того**, как `srvTryLogin()` читал
пароль → серверный вход через UI всегда отклонялся («Укажите пароль…»). Дефект присутствовал
с v100, не обнаруживался jsdom-тестами (они вызывали `srvTryLogin` напрямую) и был выявлен
браузерными E2E на живом бэкенде.

**Исправление:** снимок пароля передаётся аргументом — `srvTryLogin(passSnapshot)` /
`async function srvTryLogin(presetPassword)`; вызов без аргумента совместим (читает поле).
Контроль: smoke-проверка `SRV-LOGIN-01` + E2E s.1–s.10.

Что проверяет стенд `srv` (клиент v102 против живого FastAPI + SQLite):
вход через UI с JWT+MFA/TOTP (роль L7 из IAM, данные из СУБД: 100 организаций);
доставка событий шины опросом `/core/events`; KPI-пересчёт из СУБД; AI-цикл с принятием

токена (logout → 401 на старый токен); серверный RBAC (L0 → 403 на админ-операцию).

## Запуск

```sh
# сборка v102 (детерминированная)
python3 src11/patch_v102.py

# статическая верификация
sh src11/verify_v102.sh

# DOM-тесты (89)
make test-dom

# живой протокол интеграции (поднимает бэкенд, выполняет 17 проверок, останавливает)
make platform          # или: sh src10/run_platform.sh

# E2E: демо-стенды и платформенный стенд
make test-e2e                                          # file + http (126 сценариев)
TC_WITH_BACKEND=1 make test-e2e-srv                    # srv (10 сценариев, живой бэкенд)
```

Переменные окружения: `TC_PYTHON` (python с зависимостями backend; по умолчанию
`/tmp/venv/bin/python` → fallback `python3`), `TC_API_PORT` (8000), `TC_STATIC_PORT` (8817),
`TC_API`, `TC_DB`, `TC_WITH_BACKEND=1`.

### Особенности песочницы разработки (задокументированы для воспроизводимости)

- Контейнер 1 ГБ RAM + строгий overcommit: при живом uvicorn V8 рендерера может не
  зарезервировать CodeRange («Target crashed») → стенд `srv` локально запускается с
  `--single-process` (в CI — обычный режим, `process.env.CI`), ретраи включены.
- Фоновые процессы между bash-вызовами могут выживать в другом PID/Fs-представлении:
  `run_backend.sh` убивает устаревшие uvicorn по `/proc` (матч по exe+cmdline, защита от
  самоубийства), БД пересоздаётся на каждый прогон; порты стендов параметризованы.
- TOTP-секрет администратора читается тестами напрямую из SQLite стенда (dev-процедура;
  в промышленном контуре — `TC_FIRST_ADMIN_RUNBOOK` + процедура регистрации).

## Известные ограничения (честно)

- Протоколы имеют статус `EXECUTED_LOCAL_SANDBOX_NOT_INDEPENDENT_ACCEPTANCE`: испытания
  выполнены реально, но в песочнице разработки — это не независимая приёмка (ворота G-03
  закрываются только протоколами на согласованном стенде заказчика).
- Вариант Б (air-gap) физически не проверялся; клиентские egress-гарды проверены
  самотестом политики (7/7) и отсутствием CDN-запросов в E2E 8.2.
- `dbRestorePermissionBlock` запрещает локальное восстановление снимков при активной
  серверной сессии — в стенде `srv` импорт снимков не упражняется (поведение по проекту).
